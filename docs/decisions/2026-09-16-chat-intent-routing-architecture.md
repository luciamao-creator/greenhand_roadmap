# ADR: 对话意图路由架构（为什么「上一轮污染本轮」反复发生）

- 日期：2026-09-16
- 状态：已落地（见 §5）
- 相关：`docs/decisions/2026-09-16-chatbot-eval-system.md`（评测体系与指标口径）

## 1. 背景：同一个 bug 出现了三次

| # | 截图现象 | 当时的直接原因 | 当时的修法 |
| --- | --- | --- | --- |
| 1 | 「换个城市，广州的短途线路有哪些」被答成"库内没有收录「短途」" | 后缀 `线` 把「短途」当成线路名 | 加停用词黑名单、跳过「线路」里的「线」 |
| 2 | 「换一条难一点的线」停在聚焦；「四姑娘山现在去怎么样」答成"四姑娘山不在小鱼山步道资料范围内" | 聚焦分支排在库外实体判定**之前** | 把「本轮库外实体」判定挪到聚焦之前 + 补「换线」信号词 |
| 3 | 「什么线路适合带一家老小?」被答成上一轮的"库内暂未收录「四姑娘」" | 库外实体从 history **无条件继承** | 本文（结构性收敛） |

三次修法的共同点，也是问题反复的原因：**每次都只改「某个分支的判定条件或先后顺序」，没有改产生这些分支的结构**。缺陷于是换一个出口再出现。

## 2. 根因：`answerRouteQuery` 是一条「顺序敏感 + 多套标准 + 状态靠文本反推」的瀑布

### 2.1 「本轮在说什么」没有单一判定点
服务端每轮只有 `query + history` 文本，"本轮话题是谁"被**三套彼此独立**的启发式各自反推：

| 判定 | 实现 | 继承条件 |
| --- | --- | --- |
| 库内线路（聚焦） | `deriveFocusFromHistory` + `resolveFocusRouteId` | 无新推荐意图 **且** 无地域词 |
| 库外实体 | `findOutOfLibraryEntityInQuery` / `...FromHistory` | 无地域词（**更松**） |
| 地域 | `resolveGeoScope` | — |

同一件事（是否延续上一轮话题）写了两遍，标准还不一样。两个标准不一致时，就会出现"一边认为延续、另一边认为新话题"的组合 —— 截图 3 正是如此：聚焦侧判为「新话题」（无继承对象），库外实体侧判为「延续」（继承上一轮四姑娘）。

### 2.2 判定顺序即产品语义，但顺序没有契约与测试
`answerRouteQuery` 是 `if/return` 瀑布，**首个命中者抢答**：

```
① 本轮库外实体 → ② 聚焦(点名/继承) → ③ 历史库外实体 → ④ 地域(澄清/库外城市/范围) → ⑤ 推荐
```

插入或移动任一分支都会改变其他组合的行为。修复手段长期是"把某分支往前/往后挪"，而没有任何地方声明"当 A 与 B 同时成立时谁优先"。

### 2.3 状态靠 history 文本**无限回看**反推：无时效、无回指验证、不可见、不可清除
- 旧 `findOutOfLibraryEntity` 会倒序扫描**全部**历史 user 轮，只要某轮出现过实体就一直能被捞出；
- 没有任何"话题已结束"的概念：不带地域词/线路名的**全新问题**会被打回上上轮的实体；
- 聚焦状态有显式契约（`focus_route_id` 随请求携带、UI 可清除），**库外实体没有** —— 同一类状态，一个可靠、一个靠猜。

### 2.4 兜底与正常推荐在协议上不可区分（静默降级隐身）
四种兜底（澄清 / 库外城市 / 库外实体 / 范围无线路）都复用 `makeStaticAnswer`：`mode="recommend"`、`sources=[]`、`metrics` 全 0，且**不写埋点**。结果：
- 前端一律显示「推荐模式」；
- 评测只断言 `mode` 就 100% 通过（历史上确实假绿过一轮）；
- 埋点里看不到这些轮次，"trace 完整率"指标天然漏掉所有静默降级。

### 2.5 实体识别是开环正则，补丁驱动
`scanOutOfLibraryEntity` = 后缀表 + 60+ 汉字边界串 + 停用词黑名单。每遇到一个新口语形态就加词/加例外（"短途"→黑名单，"线路"→特判跳过），**没有正负例表锁住行为**，改动无法验证边界。

### 2.6 评测是「追加式回归网」
每张截图补 1 条用例（L4-003 → L4-004 → L4-005/006 → …），只覆盖已知坏法；而缺陷空间是 `{延续/新话题} × {库内/库外/地域} × {是否新请求}` 的组合，追加式用例追不上组合爆炸。

## 3. 目标架构

一句话：**把"本轮说什么"从散落的启发式，升级为一次显式解析 + 显式状态；兜底成为一等结果。**

1. **单一判定点**：`resolveTurnIntent(query) → { continuation, newRequest, signals }`，下游只读这份结论，不再各自扫 query 再互相否决。
2. **按边定则**：单边信号命中按该边；两边都命中或都没命中 → 默认「延续」（缺省主语的追问在多轮里远比新检索常见）。
3. **继承必须有依据 + 有时效**：库外实体继承要求「本轮确为延续」且只回溯**最近一次 user 轮**。
4. **兜底一等公民**：协议增加 `fallback_reason`，兜底写埋点，前端按原因显示标签。
5. **实体识别收敛为「候选 + 判定表」**（待办）：抽出候选提取与库内外判定两张表，配表驱动单测。
6. **评测分层**（待办）：判定表用纯函数单测穷举组合，端到端 golden 只保留链路级用例。

## 4. 为什么这样能止住「三番五次」

上面的第 1、3、4 条都不是"再补一个分支"，而是消灭产生分支冲突的土壤：

- 判定收敛到一处后，**不存在"两套标准互相打架"**的可能，新增场景只改判定表而不动分支顺序；
- 继承有时效 + 有依据后，**"全新问题"不再可能被历史实体劫持**（这正是三次 bug 的共同形状）；
- 兜底可见后，即使再出现误判，也会立刻在 UI、埋点、报告三处同时暴露，而不是等到用户截图。

## 5. 本次落地

**`lib/server/services/route-chat-service.ts`**
- 新增 `resolveTurnIntent` + `TurnIntent{continuation,newRequest,signals}`，作为全服务唯一意图判定点；`NEW_REQUEST_TOKENS` / `CONTINUATION_TOKENS` / `WHY_RE`（「为什么/为何」问原因，属追问，其中的「什么」不算开新话题）。
- `resolveFocusRouteId` 与 `findOutOfLibraryEntityFromHistory` **共用**该结论：前者 `newRequest → 退出聚焦`，后者 `!continuation → 不继承` 且只回溯最近一次 user 轮。
- `ChatAnswer` 增加 `fallback_reason`（`clarify_missing_city|out_of_city|out_of_library|region_empty`）；四个兜底构造器改为接收 `StaticCtx`，兜底路径**补写埋点**（含命中的意图信号）。

**`app/chat/page.tsx`**
- 渲染 `fallback_reason`：`兜底回答 · 库内未收录该线路`，不再一律显示「推荐模式」。

**`scripts/eval-chatbot.py`**
- 兜底护栏改为**优先读协议字段** `fallback_reason`（旧服务退回 `metrics` 全 0 启发式）；
- 报告新增「走兜底文案的用例数」与「兜底原因分布」。

**`data/eval/chatbot-golden.jsonl`**
- 新增 `L4-007`（库外实体后接**全新问题** → 不得继承）、`L6-007`（库外实体后的**真追问**「那它有难度吗」→ 仍须继承，防止一刀切误伤）。

**验证**：43 条用例（41 条计分）全绿；兜底分布 `clarify 1 / out_of_city 2 / out_of_library 4` 首次在报告中可见。

   - 意图：覆盖「新检索词 / 为什么→延续 / 回指 / 两边都命中→默认延续」等 11 例。

### 仍未做（下一步）

1. **状态显式携带**：把「本轮话题」（含库外实体）像 `focus_route_id` 一样回传给前端并由前端带回，UI 提供可见可清除的话题芯片 —— 彻底摆脱"从 history 文本反推状态"。
4. **多轮状态机**：当前仍是"每轮独立解析 + 单步继承"，若后续要支持话题栈（用户在多条线路/多个候选间切换），需要显式状态机而非再加判定分支。
