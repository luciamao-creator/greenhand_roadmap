# 2026-09-16 chatbot 评测指标体系与评测集

配套阶段 3（C 端 chatbot「什么路线适合我」）。本文回答两件事：**用什么指标判断它做得好不好**，以及**用什么样的评测集来测**。

---

## 1. 为什么现在就要建评测体系

阶段 3 交付时只有「人工看一条 query 跑通」的验证，没有回归能力。结果两个真实缺陷都是**用户截图才发现的**：

| 发现方式 | 缺陷 | 性质 |
|---|---|---|
| 用户截图 | 溯源面板顺序与文字推荐顺序口径错位（检索序 vs 推荐序） | 体验一致性 |
| 用户截图 | 已锁定单条线路时仍夹带其他线路推荐 | 模式判定错误 |
| 用户截图 | 多轮追问省略线路名后语义断裂，答成别的城市 | 上下文丢失 |
| 首次跑评测 | 答案里泄漏内部 `rt_xxx` 编号 | 工程卫生 |
| 首次跑评测 | `宝石山步道` 等含通用后缀的线路名被指代解析误杀 | 解析逻辑 bug |

结论：靠人眼看截图不是工程做法。需要**可复现、可归因、可门禁**的自动评测。

## 2. 产品诉求 → 指标映射（先定承诺，再定指标）

指标不是越多越好，必须挂在产品承诺上。下表是「承诺 → 失败后果 → 指标 → 门禁阈值」的硬映射：

| # | 产品承诺 | 一旦失败的后果 | 度量指标 | 门禁 |
|---|---|---|---|---|
| 1 | 推荐的线路真实存在，不编造 | 用户按虚构线路出行，信任崩塌 | 引用越界率、内部 id 泄漏率 | **= 0** |
| 2 | 推荐契合需求 | 答非所问，用户流失 | 推荐期望命中率 | ≥ 0.75 |
| 3 | 记得住对话上下文 | 语义断裂、反复重新推荐 | 模式判定准确率 / 聚焦线路命中率 | ≥ 0.95 / ≥ 0.90 |
| 4 | 不知道就说不知道 | 编造价票、天气、补给点 | 库外信息处理率、无匹配如实说明率 | ≥ 0.90 |
| 5 | 每条推荐都可解释（溯源） | 无法验证推荐依据 | 推荐项 100% 带 `matched_chunk` | **= 1** |
| 6 | 响应速度可接受 | 对话卡顿，用户放弃 | 生成 P95 耗时 | < 8 s |
| 7 | 单位成本可控 | 规模上来后亏损 | 平均 token / 次 | 监控不设门禁 |

> 关键取舍：**产品承诺 1 是零容忍**（幻觉类），所以门禁是 `= 0` 而非某个比例；承诺 6/7 是工程约束，先用「监控」而非硬门禁，避免早期被性能拖住迭代。

## 3. 指标体系（四层，产品口径 + 工程口径并列）

### 3.1 检索层 —— 召回与排序质量

| 指标 | 定义 | 用途 |
|---|---|---|
| Hit@K | 期望线路是否出现在 top-K 候选内 | 召回能力；不达标说明索引/切片/embedding 有问题 |
| MRR | 期望线路排名倒数的均值 | 排序质量，比 Hit@K 更敏感 |
| 分数区分度 `top1−top5` | 候选相关度极差 | **监控向量检索"平手"噪声**。实测该值常低至 0.017（0.5962 vs 0.5792），此时排序接近随机，不应据此宣称"最相关" |
| 聚焦召回正确率 | focus 模式下命中的是否就是目标线路 | 聚焦模式的前提，应恒为 100% |

### 3.2 生成层 —— 忠实度与格式护栏

| 指标 | 定义 | 用途 |
|---|---|---|
| 引用越界率 | 答案提到的线路名不在本轮溯源里的比例 | **幻觉主指标**；同时覆盖「聚焦模式夹带其他线路」这个真实缺陷 |
| 内部 id 泄漏率 | 答案出现 `rt_xxx` 的比例 | 工程卫生；已通过"候选用序号、id 不出服务端"根治 |
| 数值一致性 | 答案里的里程/耗时/爬升与 `route_card` 是否一致 | 数值幻觉（下一阶段接入） |
| 格式合规率 | JSON 可解析、`answer` 非空 | 管线健壮性 |
| 库外信息处理率 | 被问到票价/天气等库外信息时是否声明「资料未覆盖」 | 承诺 4 |

### 3.3 对话层 —— 多轮与模式判定（本产品最易错的一层）

| 指标 | 定义 | 用途 |
|---|---|---|
| 模式判定准确率 | `focus` vs `recommend` 判对的比例 | 直接对应「该聚焦时聚焦、该推荐时推荐」 |
| 聚焦线路命中率 | 一轮实际聚焦的 `route_id` 与期望一致 | 直接覆盖「多轮语义断裂」缺陷 |
| 聚焦延续率 | 省略线路名的追问仍继承正确聚焦 | L2 层专用 |
| 聚焦退出率 | 新城市/明确要新推荐时正确解除聚焦 | L4 层专用 |
| 答案有用性 | LLM-judge 0–5 分 + 人工抽检 | 主观质量（下一阶段接入） |

### 3.4 系统层 —— 工程 SLA 与成本

| 指标 | 说明 |
|---|---|
| 请求错误率 | 接口/上游失败比例 |
| 检索 P50/P95、生成 P50/P95 | 分别归因「检索慢」还是「模型慢」 |
| 平均 token/次 | prompt + completion，成本口径 |
| trace 完整率 | 每轮是否都落下 `检索`+`回答生成` 两条埋点（对齐 §9） |

## 4. 评测集设计

### 4.1 分层（按"最可能坏在哪"切，而不是按难度切）

| 层 | 意图 | 条数 | 期望 |
|---|---|---|---|
| **L1** | 单线路点名 → 聚焦问答 | 7 | `mode=focus` 且聚焦线路精确命中；**答案不得提及其他线路** |
| **L2** | 多轮指代：省略线路名的追问 | 6 | `mode=focus` 且继承正确聚焦（**只给 history，不传 focus**，压服务端能力） |
| **L3** | 城市/偏好 → 跨库推荐 | 8 | `mode=recommend` 且期望线路出现在推荐位 |
| **L4** | 聚焦中切换到新城市 / 要求新推荐 | 3 | `mode=recommend`，聚焦正确解除 |
| **L5** | 负例与边界：库外城市、库外信息、超范围意图、无上下文空泛追问 | 5 | 不编造、如实说明无匹配 |

**合计 29 条。** 分层对应的正是三次真实事故所在的位置——L1/L2 覆盖前两个截图缺陷，L5 覆盖"该说不知道"。

### 4.2 样本 schema（`data/eval/chatbot-golden.jsonl`）

```jsonc
{
  "id": "L2-001",
  "layer": "L2",
  "intent": "多轮指代：省略线路名的追问",
  "query": "有什么是相比其他路线我需要格外注意的吗",
  "history": [{ "role": "user", "content": "如果我去青城山那条线…" },
              { "role": "assistant", "content": "青城山前山步道是…" }],
  "carried_focus_route_id": null,          // 客户端会携带的聚焦；null 用于压服务端自行回溯
  "expect": {
    "mode": "focus",                        // 期望模式
    "focus_route_id": "rt_7820cc9568",      // 期望聚焦线路
    "must_recommend_any_of": [],            // 推荐位至少命中其一
    "forbid_recommend": [],                 // 禁止被推荐
    "must_say_any": [],                     // 必须出现的表述（如"资料未覆盖"）
    "no_recommendation": false,             // 期望"如实说明无匹配"
    "must_not_regex": []                    // 禁止出现的正则（如 rt_ 编号）
  },
  "review": false                           // true = 记录但门禁不计分（主观用例）
}
```

设计要点：
- **期望值是集合而非单点**（`must_recommend_any_of`）：推荐本身有多解，用"可接受集合"避免把合理答案判错。
- **`carried_focus_route_id` 默认为 `null`**：刻意不传聚焦状态，逼服务端从 `history` 自行回溯——这正是修复后生产路径的健壮性来源。
- **`review: true` 免责**：超范围意图、危险偏好这类需要人判断的用例不进门禁，避免指标虚高/虚低。

### 4.3 数据来源（三路，保证覆盖真口语与真边界）

| 来源 | 说明 | 对应层 |
|---|---|---|
| 真实埋点回流 | 从 `data/rag/chat-trace.jsonl` 挖真实 query，尤其 badcase | L1–L4 |
| 线路反向生成 | 33 条线路 ×「准备什么 / 难度 / 带孩子 / 季节」等问法 | L1、L2 |
| 人工构造边界 | 库外城市（拉萨）、库外信息（票价）、超范围意图（订酒店） | L5 |

### 4.4 增长策略

- 每次线上 badcase → 补一条用例（golden set 只增不减，作为回归基线）。
- 用例变更需在 PR 里说明，防止"改评测集让指标变绿"。

## 5. 执行链路与门禁

```
data/eval/chatbot-golden.jsonl
        │
        ▼
scripts/eval-chatbot.py  ──HTTP──▶  POST /api/chat（真实生产管线）
        │
        ├─▶ data/eval/reports/eval-chatbot-<ts>.json   机器可读（含逐条回答与检查明细）
        └─▶ data/eval/reports/eval-chatbot-<ts>.md     人读报告（总览 + 分层明细 + 失败用例）
```

设计原则：
- **不引入 LLM 裁判（默认）**：全部用确定性规则，保证 CI 可跑、结果可复现、失败可归因到具体检查项。主观指标留作 `--judge` 扩展（见 §7）。
- **打真实生产接口**而非直接调函数：把模式判定、history 回溯、prompt 组装全都纳入被测范围，避免"测了个假管线"。
- 支持 `--layer L2`、`--limit N`：改某一层时只跑该层，秒级反馈。

命令：

```bash
python3 scripts/eval-chatbot.py                 # 全量 29 条
python3 scripts/eval-chatbot.py --layer L2      # 只跑多轮指代层
python3 scripts/eval-chatbot.py --limit 5 --verbose
```

## 6. 首轮基线（2026-09-16）

数据源：`data/eval/reports/eval-chatbot-20260916-123853.md`（32 条用例 / 30 条计分）。

| 指标 | 基线 | 用例数 | 门禁 | 达成 |
|---|---|---|---|---|
| 用例通过率 | 100.0% | 30 | — | ✅ |
| 模式判定准确率 | 100.0% | 30 | ≥95% | ✅ |
| 聚焦线路命中率 | 100.0% | 15 | ≥90% | ✅ |
| 推荐期望命中率 | 100.0% | 8 | ≥75% | ✅ |
| 无匹配如实说明率 | 100.0% | 3 | ≥90% | ✅ |
| 库外信息处理率 | 100.0% | 2 | ≥90% | ✅ |
| 引用越界率 | 0.0% | 32 | =0 | ✅ |
| 内部 id 泄漏率 | 0.0% | 32 | =0 | ✅ |
| 请求错误率 | 0.0% | 32 | — | ✅ |
| 检索 P50 / P95 | 552 / 609 ms | — | — | ✅ |
| 生成 P50 / P95 | 3285 / 4325 ms | — | <8s | ✅ |
| 平均 token / 次 | 897.8 | — | 监控 | — |

### 6.1 首轮就抓出的两个真实缺陷（均已修复）

1. **内部 `rt_xxx` 编号泄漏进答案**：因为把 `route_id` 写进了喂给模型的上下文，模型原样抄进正文。修复 = 候选用 1-based 序号标识、`序号→route_id` 映射只在服务端做，**id 永不进入模型视野**。
2. **`宝石山步道`/`小鱼山步道` 等线路名指代解析失效**：原实现是「最长公共子串 + 通用词黑名单」，而黑名单判定写成了 `token.includes(generic)`，导致任何**含通用后缀的完整线路名**（`宝石山步道`.includes("步道") === true）被整条丢弃，用户点名线路反而进不了聚焦模式。修复 = 改用**别名表**（全名 / 去后缀核心名 / 核心名 ≥3 字前缀），并用城市词表挡住「厦门」这类城市名被误当线路名。

这两个缺陷**只在 L1/L2 层暴露**，且第 2 个用"青城山"这类不含后缀的名字永远测不出来——恰好印证了 §4.1「按最可能坏在哪分层、且要用多种命名风格覆盖」的必要性。

### 6.2 对基线数字的诚实解读

**100% 通过率不代表质量已经达标，只代表这套用例当下抓不出问题了。**此时它是一张**回归网**，不是质量标尺：

- 计分用例只有 30 条，L5 仅 3 条、库外信息仅 2 条——小样本下的 100% 置信度很低。
- 全部指标是确定性规则，**主观质量（答案是否真的好用）完全没测**，需要 §7 的 LLM 裁判补位。
- 指标无区分度：全绿说明用例难度尚未触到能力边界，应主动加压（更口语化、更模糊、更长多轮、含干扰线路的问法）。
- **检索层是当前真正的短板**：`identity` 模板 chunk 对泛化词虚高、短文本相关度挤在 0.55–0.60（区分度低至 0.017），候选近乎按噪声排序。它没让指标变红，只是因为 L3 的 `must_recommend_any_of` 是集合判定；换成 MRR/Hit@1 立刻会暴露。

## 7. 已知局限与下一阶段

| 局限 | 影响 | 下一步 |
|---|---|---|
| 无 LLM 裁判 | 「忠实度/有用性」主观质量未覆盖 | 增加 `--judge`：用 qwen 对「答案是否只用上下文」「是否真的回答了问题」打 0–5 分，抽检而非全量 |
| 引用越界靠全名子串匹配 | 简称（如只说"香山"）漏检 | 引入别名级匹配；或让模型输出结构化引用声明 |
| 评测集 29 条偏小 | L5 边界置信度低 | 按 §4.4 用线上 badcase 持续扩 |
| **检索层质量未达标** | `identity` 模板 chunk 对泛化词虚高，短文本相关度挤在 0.55–0.60，区分度极低，导致候选靠噪声排序 | chunk 类型加权（降 `identity`/`geo`，提 `description`）+ query 改写；这是比调 prompt 收益更大的方向 |
| 聚焦判定仍是启发式 | 边界表述可能误判 | UI 已给显式「聚焦芯片 + ✕ + 聚焦这条线」兜底；后续可加一次轻量意图分类 |
