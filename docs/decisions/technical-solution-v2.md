## 2. 技术目标

- 支撑 `精选新手路线库 + 路线跟随型导航` 的 MVP；

- 支撑首批 `20-30 条` 成熟公开新手线的录入、审核、上线与迭代；

- 支撑 `推荐解释、FAQ、checklist 组合` 三类 AI 能力；

- 支撑弱网环境下的基础可用性，但不承诺完整离线地图引擎；

- 在个人开发者可承受的成本内，保持后续扩展到 `50-100 条` 路线的可能性；

- 保持前端审美接近 `OTA App + 地图 App` 的简约清爽体验，而不是堆叠工具感界面。

## 3. 当前方案核心结论

### 3.1 已确认

- 当前 MVP 不再采用 `自定义地图图像渲染生产链`；

- 当前 MVP 采用 `路线库先筛选 + 在途导航辅助` 的产品路径；

- `AI/RAG` 只承担整理、解释、推荐、checklist 组合等辅助职责；

- 路线库只收录 `成熟公开、可查可证、适合新手` 的线路；

- 路线入库必须经过结构化审核，而不是直接抓取后上线。

### 3.2 当前推荐默认值

- `客户端载体`：正式 MVP 建议 `App 优先`，而不是小程序优先；

- `服务端`：`Next.js + API Routes` 一体化起步；

- `数据库`：`PostgreSQL + PostGIS + pgvector`；

- `地图底座`：优先选择 `国内合规、支持移动端定位与路线显示的地图 SDK`；

- `内容后台`：与 API 共用同一套 Next.js 管理后台；

- `AI 检索层`：结构化数据优先，非结构化资料仅作解释与辅助生成。

### 3.3 待最终拍板

- 客户端框架在 `Flutter` 与 `React Native` 之间最终二选一；

- 地图 SDK 在候选厂商中的最终选型；

- 地形高差表达是依赖地图 SDK 的 3D 能力，还是额外接高程数据做海拔剖面补充；

- 小程序是否保留为后续轻入口，而不是正式导航端。

## 4. 总体架构

### 4.1 架构分层

- `客户端层`

  - 路线发现；

  - 路线详情；

  - 出发前准备；

  - 在途导航；

  - 天气风险；

  - FAQ/推荐解释展示。

- `业务服务层`

  - 路线库查询；

  - 路线详情聚合；

  - AI 解释接口；

  - checklist 组合；

  - 天气与预警聚合；

  - 审核与发布后台。

- `数据层`

  - 结构化路线库；

  - 路线几何数据；

  - 证据来源库；

  - FAQ 语料；

  - 物资库；

  - 埋点与日志。

- `AI/RAG 层`

  - 资料切片；

  - 向量检索；

  - 提示词编排；

  - 受控生成；

  - 输出安全约束。

### 4.2 架构原则

- 结构化事实优先于生成结果；

- 地图真相优先于 AI 语言包装；

- 地图 API / 地图 SDK 真相优先于人工主观补点；

- 路线库小而精优先于大而全；

- 弱网降级优先于离线承诺；

- 一体化起步优先于微服务拆分。

## 5. 客户端方案

### 5.1 载体建议

- `推荐默认值`：App 优先。

- 原因：

  - 路线跟随、定位、偏航提醒更适合移动原生能力；

  - 地图 SDK、定位权限、后台保活与导航体验都比小程序更可控；

  - 更容易做出接近 OTA/地图类产品的完整 UI 体验。

### 5.2 客户端框架建议

- `优先候选：Flutter`

  - 优势：

    - UI 一致性高，做精致移动端界面效率高；

    - 适合做清爽、层级明确的卡片与底部抽屉式交互；

    - 性能稳定，地图页和列表页切换体验较好。

  - 风险：

    - 地图插件生态需要逐一核验；

    - 与国内 SDK 的原生桥接成本可能略高。

- `备选：React Native`

  - 优势：

    - 与 Next.js/TypeScript 栈更一致；

    - AI 编码协作效率高；

    - 后台和客户端可共享部分业务模型与工具代码。

  - 风险：

    - 地图 SDK 与导航相关原生能力接入可能更碎；

    - UI 细节一致性需要更多治理。

### 5.3 MVP 客户端模块

- `discover`

  - 路线发现；

  - 标签筛选；

  - 推荐位。

- `route-detail`

  - 路线详情；

  - FAQ；

  - 风险说明；

  - 出发按钮。

- `prepare`

  - checklist；

  - 出发前风险检查；

  - 天气提示。

- `on-route`

  - 路线跟随；

  - 偏航提醒；

  - 岔路/关键点提醒；

  - 下撤提示。

- `weather`

  - 当前天气；

  - 风险描述；

  - 官方预警入口。

- `profile-lite`

  - MVP 阶段可无登录，先只保留设备内状态和历史浏览缓存。

## 6. 地图与导航方案

### 6.1 核心定义

- 本产品的导航不是车机式 turn-by-turn。

- 本产品的导航定义为：

  - 用户当前位置与推荐路线同屏展示；

  - 接近关键节点时提醒；

  - 偏离推荐路线一定距离时提醒；

  - 需要收手或回撤时给出保守提示。

### 6.2 路线数据形态

- 每条路线至少包含：

  - `route_polyline`

  - `start_point`

  - `end_point`

  - `key_nodes`

  - `fork_nodes`

  - `exit_points`

  - `risk_points`

  - `bounding_box`

- 几何数据以结构化方式存储，不依赖运行时 AI 生成。

### 6.3 地图底座要求

- 中国区可稳定使用；

- 支持移动端实时定位；

- 支持 polyline、marker、polygon 等叠加；

- 支持基础 3D 或可视角度变化；

- 支持卫星图或较强地形感表达；

- 支持常见移动端地图交互与性能优化。

### 6.4 地形与海拔表达策略

- 不把“真实 3D 山体”作为 MVP 唯一前提；

- 推荐采用 `地图底座 + 海拔剖面 + 累计爬升表达` 的组合方案：

  - 地图负责空间关系；

  - 海拔剖面负责高差理解；

  - 标签负责把“累不累”翻译成人话。

- 如果选定的地图 SDK 有足够好的 3D 地形能力，可作为增强项接入。

### 6.5 偏航提醒基础算法

- 客户端持续采集当前位置；

- 服务端或本地根据当前位置与 route polyline 的最短距离做判断；

- 超过阈值时触发偏航提醒；

- 接近 fork node 时触发岔路提示；

- 接近 exit point 时允许提示“此处可收手”。

### 6.6 弱网策略

- 弱网时保留：

  - 已缓存路线基础信息；

  - 已缓存 route polyline；

  - 已缓存关键节点和 FAQ 概览；

  - 已缓存最近一次天气摘要。

- 弱网不保证：

  - 新路线搜索；

  - 实时天气更新；

  - 动态重新检索 RAG 内容。

## 7. 前端审美与交互实现原则

### 7.1 总体风格

- 参考 `OTA App` 的信息组织方式：

  - 首页轻盈；

  - 卡片清爽；

  - 标签明确；

  - 首屏决策效率高。

- 参考 `地图 App` 的空间组织方式：

  - 地图尽量全屏；

  - 操作层尽量少；

  - 通过底部抽屉承载详情；

  - 关键按钮数量克制。

### 7.2 视觉原则

- 以白色、浅灰、低饱和自然色为主；

- 避免户外极客风的重黑色块和密集按钮；

- 标签与风险色彩有明确等级，但不制造恐慌；

- 首页与详情页使用大留白、圆角卡片、轻阴影；

- 地图页采用 `全屏地图 + 半透明底部面板` 结构。

### 7.3 信息层级

- 一级信息：

  - 适不适合我；

  - 现在是否适合去；

  - 开始导航。

- 二级信息：

  - 时长、距离、爬升；

  - 标签；

  - FAQ；

  - checklist。

- 三级信息：

  - 证据来源；

  - 详细规则；

  - 次级说明。

### 7.4 工程实现建议

- 建立设计 token：

  - color；

  - radius；

  - spacing；

  - elevation；

  - typography；

  - tag styles。

- 统一沉淀基础组件：

  - RouteCard；

  - TagChip；

  - RiskBanner；

  - BottomSheet；

  - MetricRow；

  - FAQAccordion；

  - ChecklistGroup；

  - MapFloatingAction。

## 8. 服务端方案

### 8.1 推荐架构

- `Next.js`

  - 提供后台管理界面；

  - 提供 BFF/API Routes；

  - 提供内部审核工具页面。

### 8.2 为什么一体化起步

- 单人开发下，研发与运维成本最低；

- 内容后台和 API 共享业务模型；

- 便于快速调整字段、审核流和展示逻辑；

- 后续若规模增长，再拆分独立服务。

### 8.3 服务端职责

- 路线查询与聚合；

- 详情页数据拼装；

- 推荐解释生成；

- FAQ 生成与检索；

- checklist 组合与缓存；

- 天气与预警聚合；

- 路线审核、上下线和版本管理。

## 9. 数据存储方案

### 9.1 数据库

- `PostgreSQL` 作为主库；

- `PostGIS` 存储路线几何和空间信息；

- `pgvector` 存储 FAQ/资料向量索引。

### 9.2 核心表

- `routes`

- `route_tags`

- `route_geometries`

- `route_nodes`

- `route_exit_points`

- `route_risks`

- `route_sources`

- `route_faqs`

- `supply_items`

- `checklist_rules`

- `weather_snapshots`

- `publish_versions`

### 9.3 对象存储

- 存储路线封面图；

- 存储路线详情图和素材图；

- 存储海拔剖面缓存图或其他静态资源；

- 不再以大体量离线路书包为核心对象。

## 10. 内容后台与审核流

### 10.1 后台模块

- 路线基础信息录入；

- 路线证据来源录入；

- 关键节点与下撤点录入；

- 风险点录入；

- 标签与 FAQ 管理；

- checklist 规则管理；

- 路线审核与发布管理。

### 10.2 审核流

- `草稿`

  - 资料收集中。

- `待审核`

  - 已达到最小录入要求。

- `可入库`

  - 满足 A 级可信度标准。

- `已发布`

  - 可在客户端展示。

- `暂停推荐`

  - 风险上升或信息过期。

- `淘汰`

  - 不再继续维护。

### 10.3 单一事实来源

- 结构化字段为前台展示和 AI 解释的第一信源；

- 原始游记、视频、评论只作为证据，不直接作为前台展示事实；

- FAQ、推荐解释和 checklist 文案必须可回溯到结构化字段或证据来源。

## 11. AI / RAG 技术方案

### 11.1 使用边界

- `允许`

  - 资料归纳；

  - 标签候选；

  - 路线摘要；

  - FAQ 文案；

  - 推荐解释；

  - checklist 排序与组合解释；

  - 基础参数补全；

  - 来源摘要草稿。

- `不允许`

  - 在缺乏地图结果时主观生成核心路线几何数据；

  - 生成禁区边界；

  - 脱离地图 API / 结构化事实判断真实导航路线；

  - 脱离结构化事实自由发挥。

### 11.2 数据来源优先级

- 第一优先：地图 API / 地图 SDK 同步后的结构化事实层；

- 第二优先：人工核验后的证据摘要；

- 第三优先：切片后的非结构化公开资料；

- 用户上报的节点 / 下撤点 / 风险点提议在审核通过前不进入第一优先级。

### 11.3 RAG 流程

- 运营录入最小事实；

- 服务端调用地图能力补齐基础参数和空间草稿；

- 内容编辑录入原始资料；

- 服务端对资料做切片、摘要、embedding；

- 问答时先命中结构化字段；

- 若结构化字段不足，再补充检索摘要；

- 最终输出前套用受控模板，避免模型过度发挥。

### 11.5 用户上报协同

- 客户端或后台允许提交关键节点、下撤点、风险点上报；

- 上报对象进入独立待审核池，不直接写入正式事实表；

- 只有审核通过后，才可合并进 `route_nodes / route_exit_points / route_risk_points`。

### 11.4 checklist 组合机制

- 不使用完全自由生成；

- 使用 `物资库 + 规则引擎 + LLM 文案润色`：

  - 物资库定义标准物资；

  - 规则引擎按天气、时长、爬升、地形打分；

  - LLM 只负责把排序结果解释成人话。

## 12. API 设计

- `GET /api/routes`

  - 获取路线列表和筛选结果。

- `GET /api/routes/:id`

  - 获取路线详情。

- `GET /api/routes/:id/navigation`

  - 获取导航所需几何、关键节点、下撤点、风险点。

- `GET /api/routes/:id/faq`

  - 获取 FAQ 与解释数据。

- `GET /api/routes/:id/checklist`

  - 获取 checklist 组合结果。

- `GET /api/routes/:id/weather`

  - 获取天气摘要与预警状态。

- `POST /api/ai/recommend-routes`

  - 根据条件返回推荐解释。

- `POST /api/admin/routes`

  - 创建路线。

- `PUT /api/admin/routes/:id`

  - 更新路线。

- `POST /api/admin/routes/:id/review`

  - 审核状态流转。

- 不上传私有用户轨迹用于模型训练；

- 不将敏感信息写入日志；

- 地图选型优先中国区合规方案；

- 天气与预警仅作辅助提示，不替代官方管理要求；

- 风险表达坚持保守原则，避免制造“平台担保安全”的误解。

## 16. 技术风险
