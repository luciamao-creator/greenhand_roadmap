# 新手徒步路线库 MVP 后台录入与审核页面设计 V1

## 1. 文档信息

- 状态：当前生效，待业务与研发评审

- 日期：2026-09-04

- 适用范围：后台产品设计、前后端研发、内容录入 SOP、审核发布流程

- 关联需求：`docs/requirements/mvp-prd-v2.md`

- 关联候选池：`docs/requirements/first-launch-30-route-candidate-pool-v1.md`

- 关联数据：`docs/requirements/route-data-model-and-route-package-schema-v1.md`

- 关联接口：`docs/requirements/mvp-api-contract-v1.md`

- 关联表设计：`docs/requirements/database-table-design-v1.md`

- 上位约束：`SOUL.md`

## 2. 文档目标

- 定义后台如何承接 `首发 30 条路线候选池`；

- 定义一条路线从 `候选 -> 录入 -> 补证据 -> 审核 -> 发布` 的页面与动作；

- 让后台设计与数据库表、API 契约、前台页面需求形成闭环；

- 为后续 UI 设计、前端实现和内容运营提供单一事实来源。

## 3. 核心判断

- 后台不是一个“大表单”，而是一条 `内容生产流水线`；

- 新增路线默认采用 `最小人工录入 + Agent 预填 + 人工审核放行`，而不是要求运营一开始手填完整全量字段；

- 对这个项目而言，后台最重要的不是“编辑文案”，而是：

  - 让路线事实被稳定录入；

  - 让地图 API 返回的空间真相被稳定接入；

  - 让用户上报的关键节点、下撤点、风险点有待审核入口；

  - 让证据与风险被明确检查；

  - 让发布具有可追溯性；

- 因此后台必须围绕以下 5 个阶段组织：

  1. 候选池管理
  2. 路线事实录入
  3. 证据与解释补齐
  4. 审核决策
  5. 发布与回退

## 4. 后台角色定义

### 4.1 内容录入员

- 负责从候选池中拉起路线；

- 负责录入最小基础事实，并触发 Agent 预填；

- 负责确认 Agent 补出的基础参数、标签、证据来源草稿；

- 负责处理地图 API 未覆盖时仍需补齐的解释层字段；

- 不负责最终审核通过与正式发布。

### 4.2 审核员

- 负责检查新手友好度、一票否决项、证据充分性；

- 负责给出 `A / B / C` 可信度结论；

- 负责决定是否进入可发布状态。

### 4.3 用户上报审核人

- 负责审核用户提交的关键节点、下撤点、风险点提议；

- 负责决定这些提议是否合并进正式事实表；

- MVP 阶段该角色可以与审核员由同一人兼任。

### 4.4 发布操作员

- 负责在审核通过后触发正式发布；

- 负责版本说明、暂停推荐、回退发布；

- MVP 阶段该角色可以与审核员由同一人兼任。

## 5. 状态流转

### 5.1 路线主状态

- `candidate`

  - 存在于候选池，但尚未进入正式录入工作区。

- `draft`

  - 已开始录入，但未提交审核。

- `pending_review`

  - 已提交审核，等待审核动作。

- `approved`

  - 审核通过，可生成发布版本。

- `published`

  - 已正式发布给前台。

- `paused`

  - 暂停推荐，不对前台正常曝光。

- `retired`

  - 不再维护，不继续投入成本。

### 5.2 页面阶段对应关系

| 状态                           | 主要负责页面  | 主动作                  |
| ---------------------------- | ------- | -------------------- |
| candidate                    | 候选池列表页  | 拉起录入、标记优先级、补候选备注     |
| draft                        | 路线录入工作台 | 填表、补几何、补证据、保存草稿      |
| pending\_review              | 审核页     | 检查、退回、通过             |
| approved                     | 发布页     | 生成版本、预览 package、确认发布 |
| published / paused / retired | 发布记录页   | 暂停、恢复、查看历史           |

## 6. 后台信息架构

MVP 后台建议采用以下一级导航：

1. `候选池`
2. `路线工作台`
3. `审核中心`
4. `发布中心`
5. `物资与规则库`

说明：

- MVP 不单独做复杂仪表盘；

- 默认首页直接进入 `候选池`，因为当前阶段核心任务是把路线真正录进去；

- `路线工作台` 是核心生产位，不应被拆成太多一级入口，避免内容团队迷路。

## 7. 页面清单

## 7.1 AD01 候选池列表页

### 页面目标

- 承接 `首发 30 条路线候选池 V1`；

- 给内容团队一个清晰的“先录哪条”的工作列表；

- 把候选与正式录入对象分开管理。

### 核心模块

- 顶部筛选条

  - 省份

  - 城市

  - 层级 `A1 / A2`

  - 当前建议状态

  - 路线类型

- 候选池表格

  - 路线名

  - 省份/城市

  - 候选层级

  - 新手适配度

  - 主要风险备注

  - 当前建议状态

  - 最近更新时间

  - 当前工作状态

- 右侧快捷预览抽屉

  - 初步入选理由

  - 风险备注

  - 建议优先级

  - 一键进入录入

- `新建草稿` 弹窗

  - 路线名

  - 省份 / 城市

  - 景区 / 片区

  - 起点名 / 终点名

  - 路线类型

  - 地图检索关键词（可选）

### 关键动作

- `创建录入任务`

  - 将候选线转入 `draft`

  - 同时触发 Agent 执行首轮预填

- `标记为优先录入`

- `标记待补证据`

- `标记淘汰`

- `查看候选备注`

### 最小字段来源

- 直接来自 `first-launch-30-route-candidate-pool-v1.md`

- 落库建议对应：

  - `routes`

  - 候选备注可先存扩展字段或操作日志

### 页面价值

- 让后台工作真正围绕当前 30 条候选池展开；

- 让内容团队不会一上来就在数据库里“空建路线”。

## 7.2 AD02 路线工作台总览页

### 页面目标

- 作为单条路线的主工作台；

- 集中展示当前录入完整度、缺项、审核风险和下一步动作。

### 页面结构

- 顶部基础信息条

  - 路线名

  - route\_id

  - 省份/城市

  - 当前状态

  - 可信度等级

- 中部进度卡

  - 基础事实

  - 几何与导航

  - 风险与天气

  - checklist

  - 证据来源

  - FAQ 与解释

  - 用户上报待审核

- 右侧操作区

  - 保存草稿

  - 提交审核

  - 查看历史变更

  - 查看 package 预览

  - 查看 Agent 预填日志

### 关键动作

- `保存草稿`

- `提交审核`

- `查看缺项`

- `回到候选池`

- `重新触发 Agent 补全`

### 设计要求

- 不让内容录入员在多个页面之间失去上下文；

- 每个分区显示 `完成 / 缺失 / 待补证据` 状态；

- 工作台必须显式区分：

  - 运营仍需补的字段

  - Agent 待补字段

  - 用户上报待审核数量。

## 7.3 AD03 基础事实录入页

### 页面目标

- 完成路线主表 `routes` 的核心事实录入；

- 保证前台发现页、详情页能拿到稳定主信息；

- 运营在本页默认只手填最小基础事实，基础参数由 Agent 结合地图结果补全。

### 表单分组

#### A. 路线身份

- 路线名称

- route\_slug

- 省份

- 城市/区域

- 景区/片区

- 路线类型

#### B. 基本参数

- 预计时长

- 距离

- 累计爬升

- 最高海拔

- 推荐季节

说明：

- `预计时长 / 距离 / 累计爬升 / 最高海拔` 默认由 Agent 基于地图 API 或路径计算补全；

- 本页应支持 `接受建议值 / 标记异常 / 重新拉取` 三类动作，而不是默认纯手填。

#### C. 新手判断

- 一句话摘要

- 为什么适合新手

- 什么人先别去

- 最容易慌的点

- 回撤逻辑摘要

- 主路径逻辑摘要

#### D. 交通与入口

- 起点名称

- 终点名称

- 交通摘要

- 封面图 URL

- 最近核验时间

#### E. 路线标签

- 景观审美标签

- 安全感标签

- 轻松成就标签

- 是否核心标签

- 排序

### 必填校验

- 路线名称、城市、省份、路线类型必填；

- 时长、距离、爬升在提交审核前必须存在，但不要求运营创建草稿时手填；

- `为什么适合新手`、`最容易慌的点`、`回撤逻辑摘要` 必填；

- 至少补齐 1 个 `safety` 标签，且需明确 1-3 个核心标签；

- 未填完不得提交审核。

### 对应数据表

- `routes`

- `route_tags`

### 对应后台接口

- `POST /api/admin/routes`

- `PUT /api/admin/routes/:id`

## 7.4 AD04 几何、节点与导航录入页

### 页面目标

- 录入路线空间真相；

- 这是后台里最关键也最需要结构化约束的页面；

- 地图 API 是本页空间真相的默认来源，人工只负责审核、修正和接受用户上报。

### 页面结构

- 上方地图工作区

  - 路线轨迹预览

  - 起终点

  - 节点点位

  - 风险点/下撤点覆盖层

- 下方结构化表单区

  - 几何信息

  - 阶段列表

  - 节点列表

  - 下撤点列表

### 录入模块

#### A. 几何信息

- route\_polyline

- start\_point

- end\_point

- bounding\_box

- overview\_center

- overview\_zoom

- elevation\_profile\_points

补充说明：

- 如果地图 API 没有返回可用主轨迹，则路线保持缺失状态，不得通过自由备注硬补；

- 几何页要显式展示 `地图同步状态` 与 `最近同步时间`。

#### B. 阶段信息

- 阶段顺序

- 阶段名称

- 阶段类型

- 本段摘要

- 本段建议时长

- 本段风险提示

#### C. 节点信息

- 节点类型

- 节点名称

- 坐标

- 所属阶段

- 接近提示

- 纠偏提示

- 触发半径

- 用户上报待审核入口

#### D. 下撤点信息

- 下撤点名称

- 下撤类型

- 触发条件

- 建议动作

- 优先级

- 用户上报待审核入口

### 关键设计原则

- 节点、下撤点必须结构化，不允许只写在自由备注里；

- 节点、下撤点的正式事实优先来自地图 API 和审核通过的结构化上报；

- 支持“复制节点”与“按阶段批量排序”；

- 页面必须显式提醒：

  - 是否已经设置起终点；

  - 是否已有至少 1 个关键岔路点；

  - 是否已有至少 1 个下撤点。

### 对应数据表

- `route_geometries`

- `route_stages`

- `route_nodes`

- `route_exit_points`

- 风险标题

- 触发半径

- 用户上报待审核入口

#### B. 天气与时间规则

- 场景类型

- 规则说明

- 建议动作

### 页面模块

- 来源标题

- 支撑字段

#### B. 证据覆盖提示

- 是否已有官方类来源

- 是否已有地图类来源

- 是否已有体验类来源

- 是否达到“两类三份”最低要求

#### C. FAQ 列表

- 问题

- 回答

## 7.8 AD08 单路线审核详情页

### 页面目标

- 对一条路线完成最终人工判断；

- 给出通过、退回、淘汰的明确结论。

### 页面结构

- 左侧：路线摘要

  - 基础事实摘要

  - 轨迹与节点概览

  - 风险摘要

  - 证据摘要

- 中部：审核清单

- 右侧：审核结论卡

### 审核清单

#### A. 准入红线检查

- 是否存在野线倾向

- 是否主路径明确

- 是否有公共化迹象

- 是否离开成熟步道才能成立

#### B. 新手友好度检查

- 可达性

- 可理解性

- 可退出性

- 风险可表达性

#### C. 证据充分性检查

- 是否达到两类三份

- 是否有最近一年公开反馈

- 是否存在关键字段无证据支撑

#### D. 后台完整度检查

- 起终点是否齐全

- 关键节点是否齐全

- 下撤点是否齐全

- 风险点是否齐全

- checklist 是否可用

### 审核动作

- `通过`

  - 设置 `credibility_level`

  - 进入 `approved`

- `退回补充`

  - 必须填写退回原因

- `淘汰`

  - 必须填写淘汰原因

### 审核备注要求

- 退回原因不得只写“补充一下”；

- 必须明确到字段层或证据层，例如：

  - 缺官方类来源

  - 下撤点仍不明确

  - 雨天风险未写清楚

## 8. 后台主流程

## 8.1 从候选到发布的最小闭环

1. 在 `候选池列表页` 选择一条 A1 路线
2. 创建录入任务，生成 route 草稿
3. Agent 拉取地图 API 与公开资料，补齐基础参数、来源草稿、标签候选
4. 在 `路线工作台` 依次补齐：

   - 基础事实

   - 几何/节点/下撤点

   - 风险/天气/checklist

   - 证据来源/FAQ
5. 如存在用户上报，先在对应页面审核是否合并
6. 提交审核
7. 审核员在 `审核详情页` 给出通过/退回/淘汰
8. 通过后进入 `发布中心`
9. 生成 package 并正式发布

## 8.2 页面切换原则

- 录入员从 `工作台` 进入细分页面，再回到工作台；

- 审核员默认从 `审核中心列表页` 进入详情；

- 发布员默认从 `发布中心页` 操作，不回到录入页。

## 11. 对 UI 设计的约束

- 后台整体风格以效率优先，不追求复杂装饰；

- 核心区块必须支持长表单与结构化列表混排；

- 风险项、退回项、淘汰项必须使用高辨识度状态色；

- 几何与节点页建议采用 `地图工作区 + 结构表单区` 双栏布局；

- 审核页必须显式区分：

  - 事实

  - 证据

  - 解释

  - 审核结论

## 12. 当前明确不做

- 不做开放式多人协作评论流；

- 不做复杂权限矩阵；

- 不做一键 AI 自动入库；

- 不做用户侧 UGC 直接导入后台；

- 不做实时轨迹回放审核台。
